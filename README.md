# filament-max-broadcasts

Filament-плагин: **массовые рассылки** пользователям MAX-мессенджера внутри Filament-панели. Строится поверх
[`geekcodev/laravel-max-client`](https://github.com/geekcodev/laravel-max-client) (реестр чатов `max_chats`/`max_users`)
и [`geekcodev/max-php-client`](https://github.com/geekcodev/max-php-client) (API MAX).

Возможности:

- ресурс «Рассылки» (`BroadcastResource`): создание, список, просмотр, relation manager получателей;
- ресурс «Сегменты» (`BroadcastSegmentResource`): именованные группы чатов для целевого выбора получателей; на странице
  сегмента вкладки «Основное» (название/описание), «Получатели» (таблица активных диалогов с поиском, сортировкой,
  фильтром, чекбоксами, «Выбрать всех» и сохранением) и «Согласия» (журнал сегмента);
- выбор получателей при создании — сегменты (диалоги) и/или конкретные группы и каналы с серверным поиском по `chat_id`
  (снимок `recipient_chat_ids`, повторы уходят тем же людям);
- текст рассылки в формате HTML (RichEditor) с санитизацией под whitelist тегов MAX;
- тип «Новость» или «Акция» (реестр типов в конфиге, добавляются свои); для типов с настроенными кнопками —
  кнопки-диплинки в мини-приложение;
- медиа-вложения к рассылке — несколько картинок, видео и файлов (загрузка через `FileUpload`, типы и лимит из конфига)
  и отложенная отправка (`scheduled_at`);
- сбор получателей — активные чаты из реестра `max_chats` (дедуп по `chat_id`, расширяемый резолвер);
- opt-in согласие на рассылку: действие «Запросить согласие» опрашивает получателей сегмента callback-кнопками, а
  рассылка по сегменту уходит только ответившим «Да»; общий read-only журнал «Согласия» с фильтрами по сегменту и
  действию;
- статусы `scheduled → running → completed/cancelled/failed` со счётчиками `total/delivered/failed`;
- очередь `SendBroadcastJob`: лок на рассылку, батчи, ретраи, отмена, событие `BroadcastCompleted`;
- действия «Повторить» / «Отправить сейчас» / «Отменить» / «Удалить», фильтры по статусу и типу;
- права настраиваются строками (`max_broadcasts.view` / `max_broadcasts.create` / `max_broadcasts.manage`
  по умолчанию) — совместимо со spatie/laravel-permission и Gate.

## Требования

- PHP ^8.4, Laravel ^13.0
- Filament ^5.0 (панель v5), Livewire ^4.1
- `geekcodev/laravel-max-client` ^2.0 + `geekcodev/max-php-client` ^2.0
- Опубликованные миграции laravel-max-client (`max_users`, `max_chats`, `max_chat_users`)
- Работающая очередь (для фактической отправки) и **общее для всех воркеров хранилище кэша**
  (redis/database/memcached): джобы берут `Cache::lock()`; на `file`/`array` рассылку отправят два процесса параллельно,
  а счётчики разъедутся.
- Для предпросмотра вложений в админке на диске `local` — опция `'serve' => true` в `config/filesystems.php` (значение
  по умолчанию в Laravel 11+). Без неё файлы всё равно уходят в MAX, но превью и ссылки в панели не отображаются.

Плагин читает из реестра `max_chats` поля `status`, `chat_type` и `last_activity_at`. Поддерживается форма реестра 1.2
(`laravel-max-client` v2): строка на чат с `chat_id` первичным ключом, участники в `max_chat_users`, `title` у групп и
каналов. Поддержка формы 1.1.x удалена в v2.0.0: при обновлении с плагина 1.x сначала обновите `laravel-max-client` до
v2 и выполните его миграции — порядок переноса реестра описан в документации клиента. Проверить установленную версию
можно командой `composer show geekcodev/laravel-max-client`.

Колонки `max_broadcast_recipients.chat_id` и `user_id` в плагине знаковые: идентификаторы групп и каналов MAX
отрицательные, и без этого MySQL отвергал бы рассылку в канал, а на PostgreSQL тип `bigint` уже знаковый, и миграция
`0000_03_000007` приводит его к тому же виду. `0000_03_000008` делает `max_broadcast_consents.segment_id` nullable:
согласия переживают удаление сегмента, а на новых установках та же схема создаётся сразу в `0000_03_000005`.

Миграции пакета лежат в полосе `0000_03` — это позиция пакета в общем порядке миграций, который Laravel строит по именам
файлов. Полоса выбрана по графу внешних ключей: `max_broadcasts.created_by` ссылается на `users`, поэтому пакет
применяется после системных миграций приложения, а `laravel-max-client` с `max_users` и `max_chats` занимает
`0000_00`. Полная раскладка:

```
0000_00 — laravel-max-client: max_users, max_chats, max_chat_users
0000_01 — приложение, системные таблицы (users и прочие)
0000_02 — filament-max-chat
0000_03 — filament-max-broadcasts
0000_04 — приложение, доменные таблицы
```

Требование к хосту: его системные миграции, создающие `users`, должны иметь имена **меньше** `0000_03_`, иначе пакет
применится раньше них, и внешний ключ на `users` упадёт на MySQL и PostgreSQL (на SQLite такая ошибка не всплывает).
Дефолтные имена Laravel вида `0001_01_01_000001_create_users_table` этому условию не удовлетворяют: переименуйте
системные миграции приложения в полосу `0000_01_` до установки пакета. Проверить фактический порядок можно командой
`php artisan migrate:status` — она перечисляет миграции в том же порядке, в котором они применяются, то есть по именам
файлов.

## Установка

```bash
composer require geekcodev/filament-max-broadcasts
php artisan migrate    # миграции max_broadcasts, max_broadcast_recipients, max_broadcast_attachments,
                       # max_broadcast_segments, max_broadcast_consents и pivot max_broadcast_segment
                       # загружаются из пакета автоматически
```

Подключение к панели:

```php
use GeekCo\FilamentMaxBroadcasts\FilamentMaxBroadcastsPlugin;

public function panel(Panel $panel): Panel
{
    return $panel
        // ...
        ->plugin(FilamentMaxBroadcastsPlugin::make());
}
```

Права (пример со spatie/laravel-permission):

```php
Role::findByName('admin')->givePermissionTo([
    'max_broadcasts.view', 'max_broadcasts.create', 'max_broadcasts.manage',
]);
```


Имена env-переменных — в `.env.example`: права используют схему бриджа
`MAX_PERMISSION_BROADCASTS_VIEW/CREATE/MANAGE`, имя бота — общий ключ `MAX_BOT_USERNAME`, остальные настройки —
`MAX_BROADCASTS_*`. Заданная переменная перекрывает значение из конфига, а пустая строка (`KEY=`) не равна «взять
дефолт».

Настройки кнопок-диплинков по умолчанию (по типу рассылки):

```php
'bot_username' => 'my_service_bot',
'buttons' => [
    'per_type' => [
        'promo' => [
            ['text' => 'Запись на сервис', 'startapp' => 'booking'],
            ['text' => 'Консультация',     'startapp' => 'consult'],
        ],
    ],
],
```

Кнопок нет для типа, если `bot_username` пуст, для него ничего не настроено в `buttons.per_type`, либо тип переопределил
`buttonRows()` (по умолчанию `'news'` идёт без кнопок). Свои типы добавляются в реестр `types` классом, реализующим
`Contracts\BroadcastTypeContract` (простейший — трейт `Support\BroadcastTypeDefaults` + регистрация в конфиге).
Поведение типа (подписи, кнопки, цвет badge) живёт в самом типе.

### Вложения и приватность

Файлы рассылки нужны только на время отправки: `BroadcastSender` читает их с диска и загружает в MAX через
`uploadMedia`, а получателям MAX отдаёт файлы со своих серверов. Поэтому публичный HTTP-доступ к диску не требуется, и
по умолчанию вложения лежат на приватном диске `local` (`storage/app/private/broadcasts`). Диск задаётся ключом
`image.disk` и может быть любым диском Laravel: локальным публичным, локальным приватным или объектным хранилищем (S3 и
подобные).

Отправка работает с любым диском. Локальный диск отдаёт путь напрямую; файл из объектного хранилища
`Support\AttachmentFile`
скачивает во временную локальную копию (с исходным именем, чтобы оно сохранилось в MAX). Копия одна на рассылку:
`BroadcastSender` переиспользует её для всех получателей и удаляет после завершения рассылки. Ядро `max-php-client`
принимает только локальный путь, поэтому для объектного хранилища нужен доступный `sys_get_temp_dir()` с запасом под
размер одного вложения (`image.max_kb`, по умолчанию ~50 МБ); файлы сверх лимита не скачиваются.

В панели превью картинок и ссылки на файлы строятся `Support\AttachmentStorage`: для локального публичного диска —
обычный URL, для приватного локального — временная подписанная ссылка на 30 минут (нужен `'serve' => true`), для
объектного хранилища — всегда подписанная ссылка (presigned URL), даже если бакет публичный. Если файла нет или диск не
умеет временные ссылки, показывается только имя файла.

Установки, где конфиг уже опубликован, сохраняют своё значение `image.disk`. Переход на другой диск — это смена диска в
конфиге и перенос уже загруженных файлов: путь вложения хранится относительно диска, поэтому файлы со старого диска
после переключения не найдутся. Публичный локальный диск остаётся рабочим вариантом, если хост осознанно раздаёт эти
файлы наружу.

Поле «Файлы» ограничено белым списком `image.accepted_file_types` (документы и архивы; MIME проверяется сервером),
картинки и видео — `image.accepted_mime_types`. Лимит размера один для всех вложений — `image.max_kb`. Если конфиг был
опубликован до v2.0.0, ключа `accepted_file_types` в нём нет: добавьте его, иначе поле «Файлы» останется без ограничения
по типам.

## Архитектура

- `Services\BroadcastService` — создание рассылки: резолв получателей (явные чаты → сегменты, только диалоги; пустой
  выбор отклоняется), запись
  `Broadcast` + `BroadcastRecipient`, привязка сегментов, `dispatch()` очереди (с `delay()` при будущем расписании);
- `Services\BroadcastRecipientsResolver` — единственный источник списка получателей (активные чаты `max_chats`, дедуп по
  `chat_id`, сортировка по `last_activity_at`); точечная выборка по `chat_id` идёт через `resolveForChatIds()`;
- `Models\BroadcastSegment` + `Services\ConsentService` — именованные сегменты чатов; согласия хранятся по сегментам
  (факты `opt_in`/`opt_out` в `max_broadcast_consents`), стартовый сегмент «Новости и акции» создаётся миграцией как
  обычный пустой сегмент;
- `Services\ConsentRequestService` + `Jobs\SendConsentRequestsJob` — действие «Запросить согласие»: кандидаты — активные
  чаты без ответа, рассылка фиксированного сообщения с callback-кнопками;
- `Listeners\HandleConsentCallback` — приём ответов (событие `MaxUpdateReceived`), запись факта и ответ
  `answerCallback`;
- `Services\BroadcastTextSanitizer` — санитизация HTML под whitelist тегов MAX + `toMaxHtml()` (разворачивание
  `<p>`/`<div>`/`<br>` в `\n`, иначе MAX не рендерит абзацы);
- `Services\BroadcastSender` — единая точка отправки в MAX: медиавложения (картинки/видео/файлы через `uploadMedia`,
  файл из объектного хранилища скачивается во временную копию), кнопки-диплинки (`Keyboard`), сообщение с
  `TextFormat::Html`;
- `Support\BroadcastTypes` — реестр типов из конфига (`types`, token → класс контракта) для форм/фильтров/колонок:
  `options()`, `instance()`, `label()`, `badgeColor()`;
- `Contracts\BroadcastTypeContract` + `Support\BroadcastTypeDefaults` — типы как поведение: каждый тип — свой
  backed-enum, подписи/кнопки/цвет определяет сам тип (дефолты — из трейта, кнопки по умолчанию из
  `bot_username` + `buttons.per_type`);
- `Jobs\SendBroadcastJob` — очередь: `Cache::lock("broadcast:{id}")`, статус `running`, батчи по `queue.batch_size`
  с проверкой отмены и обновлением счётчиков, по завершении — `completed` + `BroadcastCompleted`;
- `Events\BroadcastCompleted` — событие завершения рассылки;
- Модели `Models\Broadcast` (`max_broadcasts`) / `Models\BroadcastRecipient` (`max_broadcast_recipients`)
  с конфигурируемыми связями `creator()` → `user_model`, `maxChat()` → `chats_model`.

Прямые вызовы `ApiClient` из Filament-страниц запрещены — отправка только через `BroadcastSender`. Текст повторно
санитизируется перед каждой отправкой.

## Приём получателей

Получатели собираются серверно из реестра `max_chats` — из формы рассылки пользователь не может подставить произвольные
чат-идентификаторы. При создании рассылки нужно выбрать хотя бы одно из полей: сегменты или получатели (если заполнено
одно, второе необязательно).

- Сегменты (`BroadcastSegment`) — в селекте рассылки показываются только сегменты с согласившимися получателями; в
  бейдже рядом с названием — их число. Сегмент может быть пустым: его можно создать заранее и наполнить позже.
  Получатели сегмента выбираются на вкладке «Получатели» страницы сегмента: таблица активных диалогов с поиском,
  сортировкой, фильтром «Только выбранные» и чекбоксами, отдельная кнопка «Выбрать всех» и счётчик выбранных. В таблице
  есть колонка согласия: часы — запрос отправлен и ждёт ответа, зелёная галочка — согласие, красный крест — отказ,
  пусто — запроса/ответа по этому сегменту нет. В сегменты попадают только диалоги: группы и каналы в сегмент не
  добавляются. Рассылка по сегменту отправляется только согласившимся диалогам, даже если в старом сегменте остались
  группы (в сегменте для этого показывается предупреждение).
- Получатели рассылки — только активные группы и каналы: диалоги вручную выбрать нельзя, они приходят из сегментов.
  Селект поддерживает серверный поиск по имени и `chat_id`; варианта «Выбрать всех» здесь нет. Если в ручной список всё
  же попал диалог (API, старые данные), сервер его игнорирует.

Выбранный список сохраняется снимком в `recipient_chat_ids`. Действие «Повторить» отправляет рассылку тем же людям, но
уважает свежие отказы: диалоги из снимка заново фильтруются по текущим `opt_in` сегментов (кто отказался после первой
отправки, повтор не получит), а группы и каналы сохраняются. Если снимка нет (рассылка создана только по сегментам),
получатели резолвятся по текущим согласиям. Чтобы расширить базовый источник чатов (фильтры, исключения, целевые
группы), замените класс резолвера через `recipients.resolver` — он должен реализовывать контракт
`resolve(): Collection<int, MaxChat>`.

У сегмента есть страница просмотра: название, описание, количество получателей и дата создания, а также кнопка
«Управлять получателями», ведущая на вкладку «Получатели». Правка и удаление на этой странице и в таблице доступны
только по праву `max_broadcasts.manage`, а сама страница — по `max_broadcasts.view`.

## Согласие на рассылку (opt-in)

Сегмент — это вручную заданная аудитория: чаты добавляются в него оператором, и он же выбирается при создании рассылки.
Согласие хранится отдельно, в `max_broadcast_consents`, и ответы состав сегмента не меняют. Поэтому у сегмента две
разные величины: все активные диалоги (кого опрашивать) и согласившиеся из них (кому уходит рассылка).

Действие «Запросить согласие» есть на странице сегмента и в строке таблицы сегментов (право `permissions.create`). Оно
ставит в очередь запрос «Вы согласны получать рассылку «название»?» с кнопками «Да» и «Нет» диалогам этого сегмента,
которые ещё не ответили. Группы и каналы не опрашиваются. Повторное нажатие безопасно: ответившие (и согласием, и
отказом) запрос больше не получают, проигнорировавшие — получают снова. Ответы принимаются слушателем на webhook
(`HandleConsentCallback`), факт записывается в `max_broadcast_consents` с привязкой к сегменту, из которого был запрос.
Payload кнопки всегда несёт сегмент (`consent:<segmentId>:<action>`); payload без сегмента игнорируется. После нажатия
сообщение с вопросом удаляется из чата (`deleteMessage`), а если удалить его не удалось — из него убираются кнопки
правкой, чтобы повторное нажатие было невозможно.

Рассылка по сегменту уходит только тем, кто ответил «Да»: отказ и молчание рассылку не получают. В селекте сегментов
показываются только сегменты с согласившимися, в бейдже — их число; выбор сегмента заполняет список получателей
согласившимися, его можно скорректировать вручную. Если у сегмента ещё нет согласий, форма попросит сначала запросить
согласие или отметить получателей вручную. Явно выбранные получатели (без сегмента) отправляются как есть.

Журнал показывает и сам запрос: каждая успешная отправка создаёт запись «Ожидает ответа» с источником «Запрос», а
нажатие кнопки заменяет её на «Согласен» или «Не согласен». Поэтому в «Согласиях» видно, кому запрос уже ушёл, но кто
ещё не ответил; фильтр по действию отделяет ожидающих от ответивших. Повторный запрос не создаёт дубль, а обновляет ту
же запись.

Общий журнал «Согласия» (`BroadcastConsentResource`) — read-only список ответов всех сегментов с фильтрами по сегменту и
действию. На странице сегмента тот же журнал открывается вкладкой «Согласия». При удалении сегмента его согласия не
удаляются: записи остаются с пустым `segment_id` и доступны в журнале фильтром «Без сегмента».

## Тестирование и разработка

PHP/Composer на хосте не требуются — всё через Docker (образ PHP 8.4, Orchestra Testbench):

```bash
docker compose up -d --build   # контейнер app (PHP 8.4)
docker compose run --rm app composer install
docker compose exec -T app composer test           # PHPUnit (SQLite in-memory)
docker compose exec -T app composer analyse        # PHPStan level max (Larastan + baseline)
docker compose exec -T app composer lint           # PHP-CS-Fixer (--dry-run)
docker compose exec -T app composer format         # PHP-CS-Fixer (исправить)
docker compose exec -T app composer coverage        # PHPUnit + отчёт покрытия и проверка порога строк (95%)
docker compose exec -T app composer security-audit # composer audit
```

Тот же набор прогоняет CI (`.github/workflows/ci.yml`) на PHP 8.4 с Xdebug в один job `quality`. Отчёт покрытия требует
Xdebug: локально в dev-образе он включён, в CI — через `coverage: xdebug` и `XDEBUG_MODE=coverage`.

## История изменений

Полные release notes по версиям — в каталоге `.agents/release/` репозитория (в архив пакета он не попадает), здесь
только значимое для пользователя.

- **v2.0.0** — синхронизация с ядром и адаптером v2.0.0 (BC): события типизированы, `HandleConsentCallback`
  принимает `MessageCallbackUpdate`, `chat_id` берётся из `message.recipient`, пользователь — из `callback.user` или
  отправителя сообщения; `answerCallback` вместо `sendAnswer`. Кнопки собираются `Keyboard`/`CallbackButton`/
  `LinkButton`, а `BroadcastTypeContract::buttonRows()` возвращает `list<list<Button>>` (кастомные типы требуют правки).
  Вложения —
  `Photo/Video/Audio/File/InlineKeyboardAttachmentRequest`, `UploadEndpoint` → token. Текст сообщения при удалении
  опроса редактируется в `TextFormat::Html` (поля `format` в теле ответа больше нет). Вложения рассылки по умолчанию
  хранятся на приватном диске `local` и показываются только в админке по временным подписанным ссылкам; для поля «Файлы»
  появился белый список типов `image.accepted_file_types`. Журнал согласий показывает и отправленные запросы («Ожидает
  ответа», источник «Запрос»), а не только ответы: видно, кому запрос ушёл и кто ещё не нажал кнопку. Кнопки страниц
  оформлены в стиле outlined и с иконками; на страницах создания рассылки и сегмента скрыта «Создать и создать ещё».
  После создания и сохранения сегмента панель возвращает на список. Лок рассылки и опроса согласия живёт не меньше
  `queue.timeout` + 60 с, поэтому долгая отправка не теряет защиту от второго воркера. Env-переменные и строки прав
  приведены к схеме MAX: `max_broadcasts.view/create/manage`, `MAX_PERMISSION_BROADCASTS_*`, `MAX_BOT_USERNAME`,
  `MAX_BROADCASTS_*`.
- **v1.1.2** — согласие на рассылку привязано к сегменту: кнопка «Запросить согласие» на странице сегмента и в таблице
  сегментов, вопрос «Вы согласны получать рассылку «название»?» с кнопками «Да» / «Нет», ответы попадают в сегмент
  запроса, а сообщение с вопросом после нажатия удаляется из чата. Payload кнопки без сегмента больше не принимается. В
  сегменты добавляются только диалоги, в селекте сегментов рассылки — только сегменты с получателями и бейджем их числа.
  Рассылка требует сегменты или получатели. В селектах появилось «Выбрать всех». Добавлены страница просмотра сегмента,
  таблица согласий на странице сегмента и бейджи chat_id / user_id. В общем журнале согласий появился фильтр по
  сегменту, включая «Без сегмента» для записей удалённых сегментов: история ответов сохраняется. Изменено поведение
  пустого выбора рассылки и тексты запроса по умолчанию: см. release notes. Одна миграция
  `0000_03_000008` делает
  `max_broadcast_consents.segment_id` nullable.
- **v1.1.1** — миграции пакета переведены в полосу `0000_03`, то есть их позиция в общем порядке миграций выведена из
  графа внешних ключей, а не из порядка установки плагинов. Переименование безопасно для существующих установок: в
  `up()` шести create-миграций стоит `Schema::hasTable()`, поэтому `php artisan migrate` на обновлении проходит no-op.
  Требуется только соблюсти требование к именам миграций приложения, описанное выше.

  в таблице получателей. При обновлении с 1.1.x: `php artisan migrate`, затем `php artisan max:upgrade`.
