# План: кнопка «Создать» на списке сегментов рассылок

> Статус: **выполнено** 2026-10-30. Ветка `dev`, релиз — patch `v1.1.2`.
> Дефект UI и прав доступа: на странице списка сегментов отсутствует кнопка «Создать», а на списке рассылок
> кнопка «Создать» не закрыта правом на создание. Оба случая — следствие поведения Filament v5, а не ошибки
> конфигурации.

---

## 1. Проблема

Страница списка сегментов (`ListBroadcastSegments`, маршрут `/broadcast-segments`) не показывает кнопку «Создать», хотя
страница создания (`CreateBroadcastSegment`) зарегистрирована в ресурсе и доступна по прямому адресу.

Ожидаемое поведение:

- кнопка «Создать» видна, если у пользователя есть право `permissions.create` (по умолчанию `broadcasts.create`);
- кнопка скрыта, если права нет;
- прямой переход на страницу создания без права отклоняется сервером с 403 (сейчас так и есть);
- то же правило действует для списка рассылок (`ListBroadcasts`), где кнопка «Создать» присутствует.

Отдельно проверяется вторая половина проблемы: на `ListBroadcasts` действие `CreateAction` объявлено без явной
авторизации, поэтому кнопку видит и пользователь с одним лишь `broadcasts.view`. Клик приводит к 403 на странице
создания, то есть сервер защищён, а UI — нет. Это нарушение принципа fail-closed в интерфейсе.

## 2. Причина

Оба симптома объясняются поведением Filament v5 (проверено по исходникам установленной версии `filament/filament`
v5.10.3).

**2.1. У `ListRecords` больше нет header-действий по умолчанию.** В Filament v3 кнопка «Создать» появлялась на любой
странице списка автоматически. В v5 `CreateAction` добавляется в сгенерированный класс страницы, а базовый
`ListRecords` не объявляет `getHeaderActions()` вовсе. `ListBroadcastSegments` переопределяет только `$resource`,
поэтому список header-действий пуст и кнопка не рендерится ни при каких правах. `ListBroadcasts` объявляет
`CreateAction::make()` явно — поэтому кнопка там есть.

**2.2. Авторизация действий не использует `Resource::canCreate()`.** На страницах ресурсов действие получает
authorization-ответ через `Page::getDefaultActionAuthorizationResponse()`, который для `CreateAction` вызывает
`Resource::getCreateAuthorizationResponse()`, а тот — общий помощник `get_authorization_response('create', $model)`. При
отсутствии политики для модели (в пакете политик нет) помощник возвращает allow, а не результат
`BroadcastSegmentResource::canCreate()`. Об этом прямо говорит комментарий в `CanBeAuthorized`:
действия не имеют автоматической авторизации и по умолчанию разрешены всем. Значит, одного
`CreateAction::make()` недостаточно: кнопку увидят все, кто вправе открыть страницу, то есть обладатели одного
`broadcasts.view`.

**2.3. Серверная защита уже корректна.** `CreateRecord::authorizeAccess()` вызывает
`abort_unless(static::getResource()::canCreate(), 403)`, а `canCreate()` в ресурсах пакета проверяет
`permissions.create` через `$user->can(...)`. Поэтому исправление касается только UI-входа и его авторизации; серверные
проверки и модели прав не меняются.

Вывод: корректная форма — объявить `CreateAction` в `getHeaderActions()` и закрыть его явным
`->authorize($createPermission)`, как это уже сделано для правки и удаления сегмента на странице просмотра и в таблице.

## 4. Порядок выполнения

### Шаг 1. Воспроизводящие тесты (ожидаемо красные)

Сначала тесты, потом код. Добавить в `BroadcastSegmentResourceTest`:

1. `testCreateActionIsVisibleWithCreatePermission` — пользователь с `can_create_broadcasts = true`, страница
   `ListBroadcastSegments`, `assertActionVisible('create')`. Сейчас падает: действия нет вообще.
2. `testCreateActionIsHiddenWithoutCreatePermission` — пользователь с `can_view_broadcasts = true` и без
   `can_create_broadcasts`, `assertActionHidden('create')`. Сейчас проходит вырожденно (действия нет вовсе) и станет
   красным, если добавить `CreateAction` без `authorize`: этим тест и держит форму фикса.
3. `testCreatePageIsForbiddenWithoutCreatePermission` — прямой `GET` на `BroadcastSegmentResource::getUrl('create')`
   без права, ожидается 403. Сейчас уже проходит; тест фиксирует серверный контракт, чтобы он не разошёлся с UI.

В `BroadcastResourceTest` — те же три теста для `ListBroadcasts`. Второй из них сейчас должен падать: `CreateAction`
без `authorize` разрешён всем, у кого есть доступ к списку.

Для Livewire-проверок использовать существующий в пакете стиль:

```php
Livewire::test(ListBroadcastSegments::class)
    ->assertSuccessful()
    // @phpstan-ignore method.notFound
    ->assertActionVisible('create');
```

Прогнать тесты и зафиксировать, что красные именно по описанным причинам: на сегментах — отсутствие действия, на
рассылках — видимость без права.

### Шаг 2. Реализация

`ListBroadcastSegments` (не забыть `use Filament\Actions\CreateAction;`):

```php
protected function getHeaderActions(): array
{
    $createPermission = config()->string('filament-max-broadcasts.permissions.create', 'broadcasts.create');

    return [
        CreateAction::make()->authorize($createPermission),
    ];
}
```

`ListBroadcasts` — добавить `->authorize($createPermission)` к существующему `CreateAction::make()`. Чтение права сейчас
инлайнится внутри `authorize` действия «Запросить согласие»; вынести его в переменную в начале
`getHeaderActions()` и использовать для обоих действий, чтобы не дублировать `config()->string(...)`.

`Resource::canCreate()` не трогать: он остаётся серверной проверкой страницы создания. В комментарии к коду ничего не
добавлять — решение фиксируется в `AGENTS.md` (gotcha) и release notes.

### Шаг 3. Прогон тестов

`composer test` — зелёный, добавленные тесты проходят. Затем `composer coverage`: новые ветки покрыты, порог 95% строк
не понижается.

### Шаг 4. Документация

1. `AGENTS.md`, раздел «Частые ошибки» — новый gotcha: в Filament v5 header-действия на страницах ресурсов авторизуются
   через политику (`get_authorization_response`), а при её отсутствии разрешены всем;
   `Resource::canCreate()`/`canEdit()` в этом пути не участвуют, поэтому для каждого действия нужен явный
   `->authorize(...)`. Там же — что `ListRecords` в v5 не добавляет `CreateAction` сам, его объявляют в
   `getHeaderActions()`.
2. `README.md`, «История изменений» — строка v1.1.2: кнопка «Создать» на списке сегментов и закрытие кнопки создания
   рассылки правом `broadcasts.create`; обновление хоста не требуется (нет миграций и изменений конфига).
3. `.agents/release/RELEASE_NOTES_v1.1.2.md` по принятому формату: «Новое» (если считать таковым появившуюся кнопку),
   «Изменение (BC)» — нет, «Затронутые сценарии», «Качество» с результатами Gate.
4. После сессии — строка в `.agents/journals/JOURNAL.md` и файл
   `.agents/journals/sessions/2026-10-30-segment-create-action.md`.

## 5. Сценарии проверки

| Пользователь             | Список сегментов          | Страница создания сегмента | Список рассылок           |
|--------------------------|---------------------------|----------------------------|---------------------------|
| `broadcasts.create`      | кнопка есть               | 200                        | кнопка есть               |
| только `broadcasts.view` | кнопки нет                | 403                        | кнопки нет                |
| без прав на рассылки     | страница недоступна (403) | 403                        | страница недоступна (403) |

Ручная проверка после сборки: под администратором кнопка «Создать» открывает форму сегмента и сохраняет его; под
пользователем с одним просмотром кнопки нет, прямой URL даёт 403; на списке рассылок поведение аналогичное.

## 6. Критерии готовности

- кнопка «Создать» на списке сегментов видна ровно при `permissions.create`;
- кнопка «Создать» на списке рассылок закрыта тем же правом, а не только доступом к странице;
- прямой заход на обе страницы создания без права отклоняется с 403, и это закреплено тестом;
- Gate зелёный целиком, включая прогон в условиях CI; покрытие не ниже 95% строк;
- `AGENTS.md`, `README.md`, release notes и журнал обновлены;
- коммит, тег и push не создаются без отдельного запроса.

## 7. Риски и ограничения

- Поведение UI меняется осознанно: пользователи с одним `broadcasts.view` перестанут видеть кнопку «Создать» на списке
  рассылок. Это исправление fail-open, публичный API, сигнатуры и ключи конфига не меняются, поэтому релиз patch-уровня;
  факт фиксируется в release notes.
- Отдельное право для сегментов (например `broadcasts.segments.create`) не вводим. Текущая модель — одно право
  `broadcasts.create` на рассылки, сегменты и запрос согласия; новое право расширило бы публичный контракт и потребовало
  бы синхронизации у всех хостов, то есть минимум minor-релиза. Если разграничение понадобится, это отдельная задача с
  планом перехода.
- Полагаться на `Resource::canCreate()` для авторизации действия нельзя: он работает на серверной странице создания, но
  не в UI. Отсюда обязательное `->authorize(...)`; при обновлении Filament поведение может измениться, поэтому тесты на
  видимость и скрытие кнопки остаются в наборе как контракт.
- Правки не затрагивают миграции и конфиг, поэтому у существующих установок после обновления пакета ничего выполнять не
  нужно.

Нет. Решения по спорным местам приняты в этом плане: право для сегментов не выделяется, авторизация действий задаётся
