## 1. Задача

Четыре связанных изменения:

1. **Запрос согласия привязан к сегменту.** Кнопка «Запросить согласие» переезжает со списка рассылок в сегмент. Запрос
   уходит получателям этого сегмента, ответы пишутся в согласия этого сегмента. Работает для любого сегмента, включая
   новые. Стартовый сегмент «Новости и акции» остаётся обычным сегментом.
2. **В сегменты — только диалоги.** Группы и каналы в сегмент выбрать нельзя. Рассылка в группы и каналы выбирается в
   получателях при создании рассылки.
3. **Рассылка требует хотя бы одно поле.** Сегменты или получатели обязательны. Заполненное одно поле делает второе
   необязательным. Валидация на форме и в сервисе.
4. **Выбор всех в селектах.** Селекты сегмента и получателей рассылки остаются с серверным поиском, но получают действие
   «Выбрать всех». Оно выбирает все подходящие чаты, а не только загруженные 50.
5. **Сегменты с получателями в рассылке.** В селекте сегментов при создании рассылки показываются только сегменты, у
   которых есть получатели. Рядом с названием выводится бейдж с количеством получателей.

## 3. Текущее состояние

- `ListBroadcasts` содержит действие `request_consent`, которое вызывает `ConsentRequestService::sendRequest()` без
  аргументов.
- `ConsentRequestService` берёт кандидатов из всех активных чатов без записи согласия. Записи ищутся по стартовому
  сегменту из `consent.segment_name` (`ConsentService::answeredChatIds()`).
- `SendConsentRequestsJob` использует общий lock `consent:send-request` и не знает про сегмент.
- Кнопки несут payload `consent:opt_in` / `consent:opt_out` без сегмента. `HandleConsentCallback` пишет запись в
  стартовый сегмент (`ConsentService::resolveConsentSegment()`, firstOrCreate по имени).
- Текст запроса в `consent.request_message` общий, кнопки «Согласен» / «Не согласен» (`button_text_opt_in/out`).
- `BroadcastSegmentForm` использует `ChatSelectionField` без ограничения типа: в сегмент можно добавить группу или
  канал.
- `BroadcastForm`: оба поля (`segment_ids`, `recipient_chat_ids`) необязательны. Пустой выбор означает «все активные
  чаты» (`BroadcastService::resolveChats()` возвращает весь реестр).
- `ChatSelectionField`: серверный поиск, но варианты и подписи выбранных ограничены `OPTION_LIMIT = 50`. Выбора всех
  нет.
- Селект сегментов в `BroadcastForm` (`segmentOptions()`) выводит все сегменты простыми названиями, без количества
  получателей и без фильтра по пустоте.
- Миграция `0000_03_000004` вставляет стартовый сегмент «Новости и акции». Выполненные миграции не правим (AGENTS §2).

## 4. Технические решения

- **Payload кнопок** получает сегмент: `consent:<segmentId>:opt_in` и `consent:<segmentId>:opt_out`. Длину payload
  проверить по спецификации max-openapi на шаге 2 (в локальном `api-reference.md` лимита нет).
- **Legacy-кнопки.** Уже отправленные опросы содержат `consent:opt_in` / `consent:opt_out` без сегмента. Такие нажатия
  относятся к стартовому сегменту (`consent.segment_name`). Ветка обязательна.
- **Текст запроса с названием сегмента.** Шаблон в конфиге с плейсхолдером `:segment`: «Вы согласны получать рассылку «:
  segment»?». Название подставляется при отправке каждому сегменту. Старые опросы сохраняют свой текст.
- **Кнопки.** Подписи по умолчанию «Да» и «Нет» (`button_text_opt_in`, `button_text_opt_out`). Текст подтверждения
  ответа без изменений по смыслу, уточняется на шаге 2.
- **Запрос только диалогам.** Кандидаты запроса — активные диалоги сегмента без ответа именно этому сегменту.
- **Право на кнопку — `broadcasts.create`.** Новое право не вводим.
- **Сегмент без диалогов** не даёт запроса: 0 получателей, уведомление «нет диалогов для запроса».
- **Группы в старых сегментах** не переписываем миграцией. При рассылке и запросе сегменты резолвятся только в диалоги,
  в инфолисте и таблице сегментов показывается предупреждение о не-диалогах.
- **Выбор всех материализует список.** Действие «Выбрать всех» записывает в поле все подходящие `chat_id`. Для рассылки
  это тот же снимок `recipient_chat_ids`, что и при ручном выборе, поэтому повтор рассылки не меняется. Режима «все
  активные» без явного списка не вводим: это противоречило бы требованию пункта 3.
- **Сегменты в селекте рассылки.** Количество получателей сегмента — число его активных диалогов, то есть тех, кому
  рассылка реально уйдёт. Сегменты с нулём не выводятся. Подсчёт делается одним проходом по всем сегментам (без запроса
  на каждый сегмент). Подпись варианта — HTML: название и бейдж количества (`fi-badge`, как в селектах чатов), поэтому
  селект использует `allowHtml()`. Сегмент, в котором остались только группы из старых данных, считается пустым.
- **Подписи выбранных без лимита.** `optionLabels()` подписывает все выбранные значения (батчами по 500), а не только
  первые 50. Иначе после «Выбрать всех» часть значений показалась бы сырыми ID.

## 8. Риски и ограничения

- **Изменение поведения рассылки в patch-релизе.** Раньше пустой выбор означал «всем активным чатам». Это изменение
  поведения и значения по умолчанию. AGENTS §5 относит такие изменения к minor-релизу. Пользователь решил выпустить всё
  в v1.1.2, поэтому изменение отмечается в release notes отдельным разделом «Изменение (BC)» и в AGENTS. Решение
  зафиксировано здесь как осознанное.
- **Изменение значений по умолчанию config.** `request_message`, `button_text_opt_in/out` меняют дефолты. Хосты, которые
  опубликовали конфиг, сохраняют старые тексты. Это описывается в release notes.
- **Старые кнопки в чатах.** Опросы до релиза содержат payload без сегмента. Legacy-ветка обязательна.
- **Группы в старых сегментах.** Миграцию с очисткой не делаем. Фильтр на резолве и предупреждение закрывают риск.
- **Подсчёт получателей в селекте.** Один проход по сегментам и диалогам должен укладываться в разумное время при сотнях
  сегментов. Если сегментов много, подсчёт кэшируется на время запроса формы.
- **Большие выборы в Select.** «Выбрать всех» при тысячах чатов может тяжело рендерить Select. Проверяется на шаге 6.
- **Lock на отправку.** Общий `Cache::lock` на каждый сегмент работает только на общем хранилище (gotcha 15).
- **Лимит payload.** Если спецификация MAX ограничивает длину, формат `consent:<segmentId>:opt_in` должен укладываться с
  запасом. Проверяется на шаге 2 до кода.
