# v1.1.1

Плагин переведён в полосу `0000_03` в общем порядке миграций приложения и всех пакетов. Позиция пакета теперь выведена
из графа внешних ключей, а не из порядка установки плагинов.

## Новое

**Полоса `0000_03`.** Полоса в имени миграции — это позиция владельца в общем порядке, а не отдельный именованный
диапазон. Laravel сортирует миграции приложения и всех пакетов по имени файла и применяет их сверху вниз, поэтому
внешний ключ допустим только на таблицу, чья миграция имеет меньшее имя. Раскладка стека i2tech:

```
0000_00 — laravel-max-client: max_users, max_chats, max_chat_users
0000_01 — приложение, системные таблицы (users и прочие)
0000_02 — filament-max-chat
0000_03 — filament-max-broadcasts
0000_04 — приложение, доменные таблицы
```

Позиция пакета следует из его FK: `max_broadcasts.created_by` и `max_broadcast_segments.created_by` ссылаются на
`users`, то есть на системные миграции приложения (`0000_01`), а `laravel-max-client` с `max_users` и `max_chats`
занимает `0000_00`.

**Тест полосы.** `tests/Feature/MigrationOrderTest.php` проверяет по исходникам, что собственные миграции лежат в
`0000_03`, что ссылки на таблицы других полос ведут назад, а ссылки внутри пакета — в более раннюю миграцию. Внутренние
ссылки проверяются отдельно: `max_broadcast_recipients`, `max_broadcast_attachments`,
`max_broadcast_consents` и `max_broadcast_segment` ссылаются на таблицы, создаваемые в `0000_03_000001` и
`0000_03_000004`, то есть порядок внутри полосы тоже значим. На SQLite нарушение не воспроизводится — таблица с внешним
ключом на несуществующую таблицу создаётся молча, поэтому проверка идёт по исходникам. Сквозную проверку по миграциям
всех владельцев выполняет `MigrationOrderTest` в приложении.

## Изменение (BC)

Переименованы все семь миграций пакета:

| было                                                       | стало                                                   |
|------------------------------------------------------------|---------------------------------------------------------|
| `0001_01_01_000001_create_max_broadcasts_table`            | `0000_03_000001_create_max_broadcasts_table`            |
| `0001_01_01_000002_create_max_broadcast_recipients_table`  | `0000_03_000002_create_max_broadcast_recipients_table`  |
| `0001_01_01_000003_create_max_broadcast_attachments_table` | `0000_03_000003_create_max_broadcast_attachments_table` |
| `0001_01_01_000004_create_max_broadcast_segments_table`    | `0000_03_000004_create_max_broadcast_segments_table`    |
| `0001_01_01_000005_create_max_broadcast_consents_table`    | `0000_03_000005_create_max_broadcast_consents_table`    |
| `0001_01_01_000006_create_max_broadcast_segment_table`     | `0000_03_000006_create_max_broadcast_segment_table`     |
| `2026_10_02_000001_make_broadcast_recipient_ids_signed`    | `0000_03_000007_make_broadcast_recipient_ids_signed`    |

Структура таблиц, состав колонок, индексы и внешние ключи не менялись: менялись только имена файлов и комментарии над
ними. В телах миграций есть одно добавление — в `up()` шести create-миграций стоит guard `Schema::hasTable()` с выходом
по `return`. Он обязателен именно из-за переименования: у установленного приложения старые имена уже записаны в таблицу
`migrations`, поэтому после обновления новые имена числятся невыполненными при уже созданных таблицах, и повторный
`Schema::create` упал бы с «таблица уже есть». У сегментов guard заодно не даёт повторно вставить стартовый сегмент.

Миграция `signed` переприменяет типы колонок на месте, и это идемпотентно: `change()` приводит `user_id` и `chat_id` к
знаковому `bigint` независимо от того, каким они были.

Требование к хосту: его системные миграции, создающие `users`, должны иметь имена меньше `0000_03_`. При дефолтных
именах Laravel (`0001_01_01_000001_create_users_table`) пакет применится раньше `users`, и внешний ключ упадёт на MySQL
и PostgreSQL; на SQLite такая ошибка не всплывает. Это не регрессия v1.1.1: при прежних именах
`0001_01_01_000001_create_max_broadcasts_table` сортировался раньше `create_users_table` по той же причине, то есть
чистая установка на хосте с дефолтными именами не работала и раньше.

В таблице `migrations` строки со старыми именами остаются как неисполняемые: на `migrate` они не влияют, но при желании
их можно удалить вручную.

## Затронутые сценарии

- Чистая установка: `php artisan migrate` проходит на PostgreSQL и MySQL в правильном порядке, все семь таблиц и pivot
  создаются. Условие — миграции приложения, создающие `users`, названы раньше `0000_03_`.
- Обновление с v1.1.0: миграции применяются повторно, шесть create-миграций выходят по `Schema::hasTable()`, фикс
  `signed` переприменяет типы, данные и схема не меняются.
- Рассылка в группу или канал: идентификаторы с отрицательным `chat_id` остаются знаковыми.
- Обновление с v1.1.1: ничего не делает, второй прогон — no-op.

## Качество

- `tests/Feature/MigrationOrderTest.php`: полоса `0000_03`, ссылки назад и порядок внутри полосы; дефект воспроизводится
  при сдвиге `create_max_broadcasts_table` в конец полосы.
- Существующий набор тестов ресурсов, сегментов, согласий и получателей — без изменений в ожиданиях.
- PHPUnit — 237 тестов, 633 утверждения, PHPStan level max и PHP CS Fixer — без ошибок, покрытие строк 97.84% при пороге
  95%.
- `composer security-audit` выполнить не удалось: `repo.packagist.org` недоступен из контейнера (curl error 28). Шаг
  Gate «в условиях CI» (чистая установка без `composer.lock`) по той же причине не выполнен и остаётся обязательным
  перед релизом.
- Порядок миграций дополнительно проверен на живой PostgreSQL в приложении: `migrate:fresh` проходит миграции в порядке
  полос, а путь обновления с v1.1.0 через симуляцию старых имён в таблице `migrations` сохраняет данные.
