# v2.0.0

Синхронизация с ядром `geekcodev/max-php-client` **v2.0.0** и адаптером `geekcodev/laravel-max-client` **v2.0.0**.
Версия ломающая: события MAX типизированы, кнопки и вложения собираются отдельными классами.

## Новое

- `HandleConsentCallback` принимает `MessageCallbackUpdate`: `chat_id` берётся из `message.recipient`, пользователь — из
  `callback.user` (или отправителя сообщения), `message_id` — из `message.body.mid`. Текст опроса для fallback-правки
  редактируется в `TextFormat::Html` (поля `format` в теле ответа больше нет).
- Кнопки: `Keyboard` + `CallbackButton`/`LinkButton`; `BroadcastTypeContract::buttonRows()` возвращает
  `list<list<Button>>`, клавиатура отправляется через `InlineKeyboardAttachmentRequestPayload`.
- Вложения: `PhotoAttachmentRequest` (token/url), `VideoAttachmentRequest`, `AudioAttachmentRequest`,
  `FileAttachmentRequest`; `UploadEndpoint` → token.
- Ответ на callback — `answerCallback()` вместо `sendAnswer()`.
- Вложения рассылки по умолчанию хранятся на приватном диске `local`: файлы нужны только для `uploadMedia`, а в MAX их
  отдают серверы мессенджера. В админке превью и ссылки строятся `Support\AttachmentStorage` по временным подписанным
  ссылкам (30 минут); без файла или без поддержки временных ссылок показывается имя файла.
- Поддержаны разные диски вложений: локальный публичный, локальный приватный и объектное хранилище (S3 и подобные). Для
  объектного хранилища файл перед загрузкой в MAX скачивается во временную локальную копию с исходным именем; копия одна
  на рассылку, переиспользуется для всех получателей и удаляется после её завершения (`Support\AttachmentFile`), файлы
  сверх `image.max_kb` не скачиваются. Ссылки в админке для таких дисков всегда подписанные.
- Поле «Файлы» получило белый список MIME `image.accepted_file_types` (pdf, doc (x), xls (x), ppt (x), txt, csv, zip):
  раньше туда принимался файл любого типа.
- Согласие на рассылку привязано к сегменту-аудитории: «Запросить согласие» опрашивает диалоги самого сегмента, которые
  ещё не ответили; ответившие (согласием или отказом) повторно не опрашиваются; рассылка по сегменту уходит только
  ответившим «Да» (отказ и молчание — нет). Состав сегмента задаётся вручную и ответами не меняется.
- Журнал согласий фиксирует и отправленные запросы: каждая успешная отправка создаёт запись `pending` («Ожидает ответа»,
  источник «Запрос»), ответ перезаписывает её на `opt_in`/`opt_out`. `pending` не считается ответом:
  получатель остаётся кандидатом на повторный опрос, а повторная отправка обновляет ту же запись, не создавая дубль.
  Джоба передаёт уже полученный сегмент, поэтому не перечитывает его на каждого получателя.
- Кнопки на страницах пакета оформлены в стиле outlined и с иконками; на страницах создания рассылки и сегмента скрыта
  кнопка «Создать и создать ещё», создание идёт через «Создать».
- После «Создать» (рассылка и сегмент) и «Сохранить» (сегмент) страница возвращает на список ресурса.
- Пустое состояние журнала согласий локализовано: «Согласий пока нет» с подсказкой вместо «Не найдено broadcast
  consents»; ключи `consent_table.empty_heading`/`empty_description` в ru/en.
- Лок очереди не истекает на середине большой отправки: TTL считается `max(queue.lock_ttl_seconds, queue.timeout) + 60`
  (`Support\QueueLockTtl`) и одинаков для `SendBroadcastJob` и `SendConsentRequestsJob`.
- «Выбрать всех» стало вариантом в самом селекте чатов (первый пункт под полем поиска) вместо отдельного действия рядом
  с полем. Оно осталось только в форме сегмента и добавляет все активные диалоги.
- Получатели рассылки без сегментов — только группы и каналы: диалоги выбираются исключительно через сегменты
  (согласившиеся). Явный диалог, переданный в обход формы, игнорируется.
- Опрос согласия и создание рассылки читают только нужные чаты: в `BroadcastRecipientsResolver` добавлен
  `resolveForChatIds()`. Штатный резолвер выбирает по `chat_id` и подгружает пользователей одним запросом; подкласс с
  переопределённым `resolve()` получает безопасный путь через свой `resolve()` (поведение сохраняется), а при желании
  ускоряется, переопределив `supportsScopedResolution()`.

## Изменение (BC)

- Constraints: `geekcodev/max-php-client` `^1.1.8` → `^2.0`, `geekcodev/laravel-max-client` `^1.2.0` → `^2.0`
  (предрелизная ветка `new` — `dev-new`).
- `BroadcastTypeContract::buttonRows()` возвращает `list<list<Button>>` вместо `list<InlineKeyboardButtonRow>`:
  кастомные типы рассылок требуют правки.
- `ConsentPoll` удалён: запрос согласия больше не притворяется типом рассылки. Кнопки собирает
  `Support\ConsentButtons::forSegment()`, а `BroadcastSender::send()` принимает необязательный тип и явные `buttonRows`.
- Callback-payload без сообщения (нет `callback.message`/`message`) не обрабатывается: чат неизвестен.
- Дефолт `image.disk` изменён с `public` на `local`. Если конфиг опубликован, значение хоста не меняется. Если хост
  полагался на пакетный дефолт, уже загруженные вложения со старого диска станут недоступны в админке до переноса
  файлов; публичный диск по-прежнему поддерживается явным значением `image.disk = public`.
- Поле «Файлы» больше не принимает произвольные типы: расширяйте `image.accepted_file_types` под свои документы. В
  опубликованном ранее конфиге ключа нет — его нужно добавить, иначе ограничение не действует.
- Вручную выбрать диалог больше нельзя: поле получателей предлагает только группы и каналы, диалоги приходят из
  сегментов. Явный диалог в `chatIds` (API, старые данные) игнорируется, а не отправляется.
- `BroadcastRecipientsResolver`/`ChatRegistry` поддерживают только форму реестра 1.2; ветки для формы 1.1.x удалены.
  Плагин требует `laravel-max-client` v2 и его миграции.
- `ConsentService::optIn/optOut/answeredChatIds/optedInChatIds` требуют `segmentId`; удалены `resolveConsentSegment()`,
  `consentChatIds()` и работа со стартовым сегментом по умолчанию. Согласие всегда привязано к сегменту.
- `BroadcastConsentAction` получил case `pending`: исчерпывающий `match` по этому enum в коде хоста нужно дополнить.
  Записи `pending` означают отправленный запрос, а не ответ, поэтому `answeredChatIds()` их не возвращает.
- `queue.lock_ttl_seconds` стал нижней границей TTL лока: фактический TTL — `max(lock_ttl_seconds, timeout) + 60`.
  Долгая отправка больше не теряет лок на середине; при жёстком падении воркера лок держится до этого TTL.
- `SendConsentRequestsJob::handle()` принимает дополнительный `ConsentService`; при ручном вызове джобы его нужно
  передать.
- Семантика согласия изменилась: раньше запрос уходил всем активным диалогам, `opt_in` добавлял чат в `chat_ids`
  сегмента, а `opt_out` удалял. Теперь сегмент — вручную заданная аудитория, ответы её не меняют, а рассылка по сегменту
  фильтруется по `opt_in`. Существующие сегменты без запросов согласия перестанут давать получателей: перед первой
  рассылкой нужно провести опрос (или выбрать получателей вручную). Повтор рассылки по сегментам больше не отправляет
  тем, кто отказался после оригинала. `ConsentService::consentChatIds()` возвращает `opt_in`-чаты из журнала, а не
  `chat_ids` сегмента. `BroadcastSegmentRecipients::dialogCounts()` заменён на `consentedCounts()`, пустой резолв
  получателей теперь отклоняется `InvalidArgumentException`.

## Затронутые сценарии

- **Запрос согласия**: кнопки «Да»/«Нет» несут `consent:<segmentId>:<action>`, ответ записывается в журнал, сообщение с
  опросом удаляется либо редактируется без кнопок. Опрос получают только диалоги сегмента без ответа.
- **Рассылка**: текст, медиа и кнопки-диплинки отправляются как раньше, изменилась сборка вложений и фильтр по согласию.
  Рассылка по сегменту — только согласившимся; явно выбранные группы и каналы отправляются как есть, диалог в явном
  списке игнорируется.
- **Повтор**: `BroadcastService::repeat()` уважает свежие отказы. Диалоги из снимка заново фильтруются по текущим
  `opt_in` сегментов: отказавшиеся после первой отправки повтор не получат, новые согласившиеся не добавляются. Группы и
  каналы из снимка сохраняются.
- **Согласия**: `opt_in`/`opt_out` обновляют журнал и не меняют состав сегмента; повторный опрос не затрагивает
  ответивших. Отправленный запрос виден в журнале как «Ожидает ответа» до ответа получателя.
