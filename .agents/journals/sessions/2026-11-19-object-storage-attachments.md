# Поддержка объектного хранилища для вложений

## Проблема

После перевода вложений на приватный диск отправка опиралась на `Storage::disk($disk)->path($path)`. Это работает только
для локальных дисков: у объектного хранилища (S3 и подобных) локального пути нет, поэтому рассылка с вложениями с такого
диска упала бы. Хосту нужен выбор диска: публичный локальный, приватный локальный или объектное хранилище.

## Решение

- `Support\AttachmentFile` готовит файл к `uploadMedia`. Тип диска определяется по адаптеру: локальный
  (`LocalFilesystemAdapter`) отдаёт путь напрямую, любой другой — скачивается через `readStream()` во временную копию в
  `sys_get_temp_dir()` с исходным именем (оно попадает в multipart), правами 0600 и проверкой размера по
  `image.max_kb` до скачивания. Ошибки чтения и отсутствующий файл дают `RuntimeException`.
- `BroadcastSender` кэширует локальные копии на время своей жизни: файл из объектного хранилища скачивается один раз на
  рассылку, а не на каждого получателя; копии удаляются в деструкторе (одна рассылка — один инстанс отправителя в
  `SendBroadcastJob`). Это же убирает повторное скачивание при частичных сбоях получателей.
- `AttachmentStorage::isPublicDisk()` отдаёт прямой URL только локальному публичному диску. Объектное хранилище всегда
  идёт через подписанную ссылку (`temporaryUrl()`), даже если бакет публичный; локальный приватный — тоже подписанная
  (нужен `'serve' => true`).
- Дефолт `image.disk` остаётся `local`; настройка принимает любой диск Laravel.

## Нюансы

- В Laravel 13 `FilesystemAdapter::path()` не бросает исключение для нелокальных драйверов, а возвращает путь от пустого
  root. Поэтому тип диска определяется через `instanceof LocalFilesystemAdapter`: так исключён случай, когда
  относительный «путь» удалённого диска совпадёт с локальным файлом в рабочем каталоге.
- Ревью ветки против `AGENTS.md` выявило устаревшие ссылки на v1 в документации после синхронизации с ядром v2:
  `sendAnswer` → `answerCallback`, `InlineKeyboardButtonRow`/`ButtonType` → `Keyboard`/`LinkButton`/`CallbackButton`,
  `UploadType→AttachmentType` → DTO вложений. Исправлено в `AGENTS.md` (§4, §5, §9) и `README.md`.
- Из debug-лога загрузки убраны `token` и `url` результата (A02: не логировать токены), осталось `has_token`.
- Временный каталог должен вмещать одно вложение (до `image.max_kb`, ~50 МБ) — требование к хосту зафиксировано в README
  и `AGENTS.md`.
- Покрытие снизилось с 97.18% до 96.68% из-за защитных веток (невозможность создать временный файл, сбой копирования,
  сбой прав), которые без моков не воспроизвести; порог 95% не менялся.
- Открытый остаток, требующий подтверждения по API MAX: токен загруженного вложения можно переиспользовать между
  получателями. Сейчас, как и до изменений, вложение загружается в MAX на каждого получателя; переиспользование токена
  сократило бы трафик, но это решение о поведении API, а не оптимизация кода.
