# Порядок миграций: полоса `0000_03`

## Что было

Пакет занимал полосу «плагины после адаптера»: миграции назывались `0001_01_01_000001`…`0001_01_01_000006`, а фикс
знаковых идентификаторов — `2026_10_02_000001` по дате. Позиция была случайной, а §2 `AGENTS.md` прямо запрещал
переименовывать выполненные миграции, потому что сдвиг имён ронял у хоста повторный `Schema::create`.

## Решение

Полоса в имени миграции — это позиция владельца в общем порядке, а не отдельный именованный диапазон. Laravel сортирует
миграции приложения и всех пакетов по имени файла и применяет сверху вниз, поэтому внешний ключ допустим только на
таблицу, чья миграция имеет меньшее имя. Раскладка стека i2tech:

```
0000_00 — laravel-max-client: max_users, max_chats, max_chat_users
0000_01 — приложение, системные таблицы (users и прочие)
0000_02 — filament-max-chat
0000_03 — filament-max-broadcasts
0000_04 — приложение, доменные таблицы
```

Позиция пакета выведена из его FK: `max_broadcasts.created_by` и `max_broadcast_segments.created_by` ссылаются на
`users`, то есть на системные миграции приложения (`0000_01`), а `laravel-max-client` с `max_users` и `max_chats`
занимает `0000_00`.

Миграции:

- `0001_01_01_000001…000006` → `0000_03_000001`…`0000_03_000006`;
- `2026_10_02_000001_make_broadcast_recipient_ids_signed` → `0000_03_000007_make_broadcast_recipient_ids_signed`.

Последняя перестала быть датированной по другой причине: дата в имени означала «сделано позже всех остальных», а в
полосе важно только «сразу за своей create-миграцией».

## Правило §2 переписано

«Миграции нельзя переименовывать» заменено на две отдельные вещи: тело выполненной миграции править нельзя, а
переименовывать можно — только вместе с `Schema::hasTable()` в `up()`. После смены имени миграция числится невыполненной
при уже существующей таблице, и без guard повторный `Schema::create` падает «таблица уже есть», то есть ломается ровно
та установка, ради которой переименование и делается. Guard стоит во всех шести create-миграциях; у сегментов он заодно
не даёт повторно вставить стартовый сегмент.

## Тесты

`tests/Feature/MigrationOrderTest.php` проверяет по исходникам, что миграции лежат в `0000_03`, что ссылки на
`users` ведут в более раннюю полосу, а ссылки внутри пакета — в более раннюю миграцию. Внутренние ссылки проверяются
отдельно: получатели, вложения, согласия и pivot ссылаются на таблицы из `0000_03_000001` и `0000_03_000004`, то есть
порядок внутри полосы тоже значим. На SQLite нарушение не воспроизводится, поэтому проверка идёт по исходникам.
Регрессия проверена: перенос `create_max_broadcasts_table` в конец полосы роняет тест на ссылке из получателей.

Сквозную проверку по миграциям всех владельцев выполняет `MigrationOrderTest` в приложении.

## Нюансы

Требование к хосту, которого нет в коде: его системные миграции, создающие `users`, должны иметь имена меньше
`0000_03_`. При дефолтных именах Laravel пакет применится раньше `users` и внешний ключ упадёт на MySQL и PostgreSQL, а
на SQLite ошибка не всплывёт. Это не регрессия: при прежних именах `create_max_broadcasts_table` сортировался раньше
`create_users_table` по той же причине. Требование зафиксировано в README, порядок проверяется `migrate:status`.
