# Статус «Ожидает ответа» в журнале согласий

## Проблема

После нажатия «Запросить согласие» сообщения уходили, но строк в журнале согласий не появлялось: таблица писала только
факты ответа, а факт отправки запроса сознательно не фиксировался. Оператор не видел, кому запрос уже ушёл и кто ещё не
ответил, — приходилось гадать по числу получателей сегмента и журналу ответов.

## Решение

- `BroadcastConsentAction` получил case `pending`; записи `pending` означают отправленный запрос, а не ответ.
- `ConsentService::requestSent()` фиксирует успешную отправку (`source = request`) условным `UPDATE` только по
  pending-строке: ответ (`opt_in`/`opt_out`) запросом не перезаписывается, дубль не создаётся, повторный запрос
  обновляет ту же запись и её `updated_at`.
- `answeredChatIds()` фильтрует `pending`: для повторного опроса такие получатели остаются кандидатами, а ответившие —
  нет. Правило «рассылка по сегменту только по `opt_in`» не изменилось.
- `SendConsentRequestsJob` пишет `pending` после успешной отправки. Ошибка записи журнала логируется и не роняет джобу,
  иначе ретрай продублировал бы уже отправленный запрос.
- В таблице согласий `pending` — серый бейдж «Ожидает ответа»; источник переводится в «Кнопка»/«Запрос» (неизвестное
  значение показывается как есть). Фильтр по действию теперь включает ожидающих.
- Документация обновлена: раздел согласия в README, §5 и gotcha 30 в AGENTS.md, release notes v2.0.0.

## Тесты

Новые unit-тесты: enum-подписи, `requestSent` (pending, защита ответа, идемпотентность, неизвестный сегмент),
`answeredChatIds` без pending, кандидаты на повторный опрос. Job-тесты: pending после отправки, отсутствие записи при
ошибке отправки, одна строка при повторном запросе, продолжение работы при ошибке записи журнала. Feature-тесты: pending
в общем журнале и на странице сегмента, фильтр по действию, перевод источника и fallback для неизвестного значения.

Итог: 346 тестов / 984 утверждения.

## Нюансы

- `pending` — не согласие и не ответ: рассылку такой получатель не получает, пока не нажмёт «Да».
- Повторная отправка обновляет ту же строку (уникальный индекс `segment_id + chat_id`), поэтому дублей нет.
- Запись `created_at` показывает первое попадание в журнал; при повторе строка не пересоздаётся.
- При удалении сегмента `pending`-записи, как и ответы, остаются с `segment_id = null` — история журнала сохраняется.
