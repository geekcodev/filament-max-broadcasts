## Сделано

1. **`BroadcastService::create()` — транзакция + валидация вложений до записи.** Раньше `saveAttachments()` мог бросить
   `InvalidArgumentException` уже ПОСЛЕ сохранения `Broadcast` — рассылка оставалась в БД «висяком» (Running/Scheduled,
   0 получателей, без вложений, джоба не поставлена). Теперь: `validateAttachments()` вызывается до какого-либо
   DB-запроса, всё создание (broadcast + `segments()->sync()` + вложения + `recipients()->createMany()`) обёрнуто в
   `DB::transaction()`, `dispatch()` вызывается уже ПОСЛЕ коммита (не ставится джоба, если откат). Упорядочено: тип →
   вложения → резолв чатов → транзакция.
2. **`ConsentService::resolveConsentSegment()` — уважает `segment_model` из конфига.** Раньше хардкодил
   `BroadcastSegment`, игнорируя `segment_model` (рассинхрон с контрактом переопределяемых моделей). Теперь резолв через
   `config('filament-max-broadcasts.segment_model')` с фолбэком на пакетную модель.
3. **`ConsentService::record()` — атомарный пересчёт `chat_ids` (устранён lost update).** Было read-modify-write JSON:
   два параллельных callback'а могли затереть список (оба читали одну базу). Теперь `record()` выполняется в
   `DB::transaction()`: факт пишется `updateOrCreate`, а `chat_ids` сегмента **пересчитывается целиком** из
   `max_broadcast_consents` (все `opt_in` для целевого сегмента). Список — производное, самовосстанавливающееся,
   поведение для существующих тестов не изменилось.
4. **`SendBroadcastJob` — устойчивость.** (а) guard: повторный прогон по уже `Completed` рассылке выходит из `send()`
   (вместо повторного `BroadcastCompleted`); (б) проверка отмены выполняется и на индексе 0 батча
   (`$index % $batchSize === 0`) — раньше первый получатель мог успеть получить сообщение, если отмену поставили перед
   стартом; (в) `error` получателя в БД обрезается до `ERROR_MAX_LENGTH = 1000` через `mb_substr` (лог остаётся полным).
5. **`delete()` в lock-guard джоб — оставлен осознанно, задокументирован комментарием.** При разборе выяснилось, что
   замена на `release()` создала бы реальные регрессии: параллельная (дублирующая) джоба после освобождения lock'а
   нашла бы перечисленных-в-`pending` получателей и отправила повторно (двойная отправка), а при исчерпании `tries`
   пометила бы рассылку `Failed` ложно. Поскольку держатель lock'а гарантированно доводит работу до конца (согласие —
   кандидаты резолвятся на момент выполнения; рассылка — все pending обрабатываются синхронно), `delete()` дубликата
   корректен и безопасен. Поведение не менялось — уточнён только смысл.
6. **Тесты.** +4: `BroadcastServiceTest::testCreateWithInvalidAttachmentPersistsNothing` (после исключения в БД не
   остаётся ни рассылок, ни вложений — регрессия на транзакцию/порядок валидации);
   `ConsentServiceTest::testResolveConsentSegmentUsesConfiguredSegmentModel` (fixture `Tests/Fixtures/OffersSegment`,
   наследует `BroadcastSegment`, сегмент согласия создаётся через переопределённую модель);
   `SendBroadcastJobTest::testHandleSkipsAlreadyCompletedBroadcast` + `testHandleStoresTruncatedRecipientError`.

## Решения / отклонения

- **`delete()` vs `release()` в джобах** — осознанно оставлено `delete()`, см. п.5 (это «разворот» моего же раннего
  замечания из аудита — здесь глубже разобран риск двойной отправки и ложного `Failed`).
- **Загрузка всех активных чатов в CheckboxList формы получателей/сегментов не менялась** — это свойство нативного
  Filament-компонента (опции нужны целиком для выбора), полное решение = пагинация/виртуализация, что выходит за рамки
  текущего объёма. Явно оставлено как известный tradeoff.
- PHPStan level max: отказ от `array_map('intval', ...)` (не проходит по типам) и от `(int)` каста `mixed` — вместо
  этого выборка `->get()->map(fn (BroadcastConsent $consent): int => $consent->chat_id)` через каст модели (как в
  `answeredChatIds()`); `mb_strlen((string) $failed->error)` из-за nullable-колонки.
